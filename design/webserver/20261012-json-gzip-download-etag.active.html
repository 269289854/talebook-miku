开启 JSON 响应 gzip 压缩并在元数据写回后刷新下载 ETag

为弱网客户端优化 Tornado JSON 接口传输体积，并修复元数据写入书籍文件后旧 ETag 缓存未清理导致的文件传输与断点续传隐患。

状态：ACTIVE 创建日期：2026-10-12 所属模块：webserver 影响范围：Tornado HTTP 传输与下载缓存 需求来源：Moke 客户端弱网优化

1. 原始诉求

“为弱网客户端（Moke 桌面/移动端）做两项后端小修，只改代码，不涉及部署：1. JSON 压缩：现在 Tornado 没有开启响应压缩，nginx 的 gzip on; 只压缩 text/html，所以 /api/* 的 JSON 全部未压缩传输；2. 下载 ETag 刷新：save_book_meta 会原地改写 EPUB/AZW3/PDF 文件，但没有清缓存，导致之后一直返回旧 ETag。”

2026-10-12 后续授权：拉取最新 TaleBook/Moke 并保留本地设备认证功能，基于当前健康镜像构建最小覆盖镜像并部署；用户随后授权将相关修复提交到两个仓库 main，不发布版本或修改私有内容的 Cloudflare 缓存配置。

在移动网络或高延迟场景下，Talebook 的 /api/* JSON 响应（包含书籍列表、搜索结果等大文本数据）未经压缩传输，显著增加了数据传输量与首屏等待时间。同时，当通过管理或编辑界面将书籍元数据同步写回书籍文件（EPUB、AZW3、PDF）后，StaticFileHandler 进程内 ETag 缓存未失效，导致客户端下载可能命中过期的 304，或在 Range 断点续传时拼接新旧切片造成文件损毁。

2. 目标与边界

目标

  • 实现 JsonGZipContentEncoding，在 Tornado 应用层对 application/json 响应且客户端携带 Accept-Encoding: gzip 时启用 gzip 压缩。
  • 严格排除书籍二进制文件、纯文本（TXT）、图片及 Range 分片请求（206 Partial Content / 含 Content-Range），避免破坏断点续传字节偏移。
  • 在 save_book_meta 成功写回任一格式后调用 web.StaticFileHandler.reset() 清理旧 ETag 缓存。
  • 提供无 Calibre 依赖的单元测试，覆盖 JSON 压缩、非 JSON 排除、Range 请求保护、ETag 304 与元数据写回 ETag 重置。

非目标

  • 不修改 nginx 生产配置文件或反向代理设置。
  • 不变更现有 API 数据格式、请求参数或响应 JSON 字段。
  • 不修改前端 app/ 代码（纯后端传输层优化）。
  • 不修改外部电子书文件的存储路径与归档机制。

3. 现状、根因与证据

观察权威证据结论
/api/* 接口返回大 JSON 时体积未压缩 webserver/main.py:297 创建 web.Application 时未配置 transforms，Tornado 默认不启用输出变换；Nginx 反向代理层仅对 text/html 开启 gzip 应在 Tornado 应用层显式注册自定义压缩变换，仅处理 application/json
书籍元数据更新后客户端下载可能返回过期 304 或续传损坏 webserver/handlers/base.py:546 使用 open(file_path, "rb+") 原地写回文件，但未调用 StaticFileHandler.reset()；而 webserver/handlers/publication.py:71 已有重置处理 原地文件改写后旧 ETag 残留，导致基于文件路径的静态缓存与实际文件内容不一致
断点续传（Range 请求）如果被压缩会导致偏移计算错误 RFC 9110 规范与 Range 协议：Range 响应必须针对原始内容字节范围（Content-Range），gzip 变换会改变传输字节流 变换层检测到 206 状态码或 Content-Range 响应头时必须立即禁用 gzip

4. 方案

方案结论：在 webserver/http_compress.py 封装 JsonGZipContentEncoding，继承 Tornado GZipContentEncoding，限制仅对 application/json 压缩，并对 206 / Range 响应放行；在 webserver/main.py 的 web.Application 构造中注入该 transform；在 webserver/handlers/base.py:save_book_meta 成功写回格式后调用 web.StaticFileHandler.reset()。
Step 1 请求过滤

客户端带 Accept-Encoding: gzip 请求 Tornado 接口

Step 2 变换分流

仅 application/json 且非 206 / Content-Range 时开启 gzip 压缩

Step 3 缓存一致

书籍元数据改写成功后主动重置 StaticFileHandler ETag 缓存

关键代码设计

# webserver/http_compress.py
class JsonGZipContentEncoding(GZipContentEncoding):
    CONTENT_TYPES = {"application/json"}

    def _compressible_type(self, ctype: str) -> bool:
        if not ctype:
            return False
        return ctype.split(";")[0].strip().lower() == "application/json"

    def transform_first_chunk(self, status_code, headers, chunk, finishing):
        if status_code == 206 or "Content-Range" in headers:
            self._gzipping = False
        return super().transform_first_chunk(status_code, headers, chunk, finishing)

# webserver/handlers/base.py: save_book_meta
if success_formats:

5. 影响范围、无界面影响与风险

影响范围

仅限 Tornado HTTP 输出变换层（JsonGZipContentEncoding）与书籍元数据持久化写回（save_book_meta）。上游 Nginx 或 Cloudflare 会自动透传带有 Content-Encoding: gzip 的响应。

保持不变

Nginx 配置、原生产 Dockerfile、前端代码、书籍下载路由、OPDS、RSS 与非 JSON 请求保持原样传输。新增独立覆盖 Dockerfile 与精确注入脚本，不替换已部署的认证和书籍处理器。

无界面影响判断依据： 本改动为纯后端 HTTP 传输层与静态文件缓存重置，不涉及任何前端页面、Vue 组件、DOM 结构、样式布局、文案或 API JSON 返回数据结构的变更。客户端（包括 Web 浏览器与第三方客户端）在 HTTP 协议层透明解码 gzip，用户可感知体验仅为加载耗时减少；元数据保存操作的用户反馈文案保持完全一致。依据 AGENTS.md 规范，该纯后端改动豁免 interface-review 审查。
主要风险与缓解：
  • CPU 开销：动态 gzip 压缩增加计算开销，未进行负载基准测试。缓解：保留 Tornado 最小长度限制，短 JSON 跳过压缩，仅处理需要压缩的 JSON。
  • 二进制与 Range 损坏风险：若错误压缩了下载流或切片流会导致续传错位。缓解：覆盖 _compressible_type 严格限制仅 application/json，并在 transform_first_chunk 中对 206 和 Content-Range 主动解除压缩。
  • ETag 缓存全局失效：StaticFileHandler.reset() 清空进程内所有静态文件 ETag 缓存。缓解：清空仅导致后续首次请求重新计算文件哈希，属于无副作用的常规安全恢复机制。
回滚方式：部署工具在切换失败时恢复备份 Compose 与旧固定镜像并等待健康检查。生产数据目录保持原位；本次未触发生产回滚。隔离 Calibre 回归验证了覆盖发布的数据回滚。
